Router-owned LLM switching path

This PR keeps the router as the conversation's active agent.llm and moves manual route selection into RouterLLM. The server and TypeScript client get additive /model_router endpoints so callers can inspect, manually switch, and resume automatic routing without replacing the whole LLM object.

★ Compatibility: the existing switch_llm and switch_profile paths remain unchanged. New APIs are additive and are intended as the future migration path.

API before → after

Before

POST /api/conversations/{id}/switch_llm
{ "llm": { ... } }

POST /api/conversations/{id}/switch_profile
{ "profile_name": "..." }

Switching replaced agent.llm. A router could auto-select internally, but callers had no stable API to select one of its registered routes.

After

GET  /api/conversations/{id}/model_router
→ { enabled, routing_mode, selected_llm_key, available_llms }

POST /api/conversations/{id}/model_router/switch
{ "llm_key": "secondary" }

POST /api/conversations/{id}/model_router/auto
{}

The conversation still points at the router. Manual switching updates routing_mode and selected_llm_key on the router-owned state.

Core behavior change

Changed areas

SDKRouterLLM state

openhands-sdk/openhands/sdk/llm/router/base.py adds routing_mode, selected_llm_key, manual/auto methods, and delegates all sync/async LLM entry points through the selected route.

SDKConversation API

LocalConversation.switch_routed_llm() and resume_auto_llm_routing() update router state while reusing the existing safe LLM replacement path and state synchronization.

ServerREST endpoints

conversation_router.py adds status, manual switch, and auto-resume endpoints. Invalid keys or non-router conversations map to 400.

ClientTypeScript parity

ConversationClient, ConversationManager, and RemoteConversation expose matching helper methods plus ModelRouterStatus.
