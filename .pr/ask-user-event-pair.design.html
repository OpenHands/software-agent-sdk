ask_user: request/response event pair + endpoint

Issue #5571 · builds on the ask_user tool from #5570

Why

The ask_user tool (#5570) pauses a run so the agent can ask structured questions. That first slice carried the answer back through the ordinary send_message() path as a user message, which the SDK had to guess was an answer rather than a normal turn. This slice gives the pause a first-class, typed transport: a request event when the run pauses, a response event when it is answered, and a dedicated endpoint to record the answer and resume.

What changes

Before

  • Answer arrives as a MessageEvent(source="user").
  • SDK parses the message text to decide if it is an answer.
  • No way for a client to match an answer to a specific request.
  • No in-band record that a question was asked or answered.

After

  • Run pauses with AskUserRequestEvent (typed request_id).
  • Answer is an AskUserResponseEvent posted to a dedicated endpoint.
  • Answer is matched by request_id; mismatches are 409.
  • Both events are visible in history; neither enters the LLM stream.

Event pair

EventSourceKey fields
AskUserRequestEvent agent request_id, questions: list[QuestionInfo], action_id, tool_call_id, tool_name, optional timeout_seconds
AskUserResponseEvent user / environment request_id, action: accept|decline|cancel, answers: dict[str, list[AskUserAnswer]]

Both subclass Event directly (not LLMConvertibleEvent): the agent observes the answer via the tool observation, so the raw pair must stay out of the LLM view — the same reason PauseEvent does.

Flow

agent calls ask_user
      │  ResponseDispatchMixin._handle_ask_user_actions
      ▼
AskUserRequestEvent emitted  ──►  run pauses (WAITING_FOR_CONFIRMATION)
      │
      │  client POSTs /events/respond_to_ask_user {request_id, action, answers}
      ▼
EventService.respond_to_ask_user  ──►  AskUserResponseEvent recorded  ──►  run resumes
      │
      ▼
_run loop resolves the pending action into an AskUserObservation (the tool result)

Endpoint

POST /api/conversations/{conversation_id}/events/respond_to_ask_user
{
  "request_id": "<AskUserRequestEvent.request_id>",
  "action": "accept" | "decline" | "cancel",
  "answers": {"auth": [{"option_id": "jwt", "label": "JWT bearer tokens"}]}
}
  • 200 answer recorded and run resumed.
  • 409 request_id does not match the single pending request (AskUserRequestError).

Invariants

  • One pending request. A second ask_user while one is open is rejected with a corrective observation, not a second pause.
  • Answer never becomes a user turn. The response resolves the pending tool call; it is not appended as an unrelated message.
  • Run always unblocks. A timeout, conversation close, or crash recovery resolves a stranded request as cancel.
  • State lock off the event loop. Server paths read the pending request in a worker thread, never holding ConversationState's lock on the loop.

Compatibility

  • Additive: a new event pair and a new endpoint; no existing REST contract changes.
  • TypeScript client gates the feature on agent-server 1.54.0 via AgentServerFeatureRequirements.askUser.
  • ask_user_timeout_seconds defaults to None (wait indefinitely), so existing deployments are unaffected.
