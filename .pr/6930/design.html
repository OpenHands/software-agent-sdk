Installed plugins reach Docker conversations

Fix for issue #6930. The outer server knows its installed plugins, but a new per-conversation container has a separate persistence directory. Its ordinary SDK installed-plugin discovery therefore sees no host-installed plugins.

Change

Before: server installed store → missing boundary → container ambient discovery
After:  server installed store → private payload snapshot → container ambient discovery

Before starting a new or reprovisioned container, the registry copies enabled installed payloads into that runtime's existing private persistence directory. The SDK loads them through its existing ambient-plugin path. No explicit attachment, new mount, public API, or persisted schema field is introduced.

  • Only snapshots marked as server-owned are reconciled. Disabled or uninstalled server plugins are removed on reprovision; an already running container keeps its snapshot.
  • Explicit attachments retain the SDK's existing precedence and persistence. Container-local installations with the same name are not replaced.
  • Copy installed payloads rather than re-fetching sources, so offline sources still work. Read host metadata without rewriting it; omit fetch URLs, host installation paths, and .git directories from the runtime snapshot.
  • Use existing path-containment checks and preserve symlinks without dereferencing host targets during copying. Stage each payload before replacement and atomically write target metadata.
  • Discovery or copy failures log a warning and do not fail conversation creation. Corrupt host metadata preserves the last snapshot; one failed payload copy does not prevent other payloads from being copied.

Environment and limits

macOS arm64 host, Python 3.13.12, Docker Desktop 4.82 / Engine 29.6.1; official Linux arm64 slim image from the same base SHA. Each test container uses 1 CPU and 2 GiB. The fix only changes the outer server, so the unmodified same-base runtime image exercises the new transport.

Messages use run=false: plugin loading, command activation, shell hooks, and MCP connection are real; model inference and generated answer quality are not tested. The full python image pull stalled, so the slim variant was used. Full-image/browser/in-container Docker, x86_64, GPU and multi-node behavior are not claimed.

The skipped related test is the existing opt-in worktree live test. The default suite deselects Docker-live cases; all ten new cases were explicitly run separately. An earlier harness iteration used the wrong event-list route; that harness error was corrected before the final before/after run and is not counted as a product failure.
