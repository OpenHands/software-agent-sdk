PR #5685 · design review

Verify cached Git refs before installation

Cold and warm caches now use one requested-ref resolver. It selects the remote identity, fetches its content, verifies its commit, and checks out that commit in detached mode.

1One resolver owns ref identity

★ Main decision: An explicit ref now produces its exact commit, uses an exact cached identity during an allowed network fallback, or fails. It cannot silently return an unrelated cached checkout.

Before: cached_repo.py:264, cached_repo.py:334. After: cached_repo.py:195, cached_repo.py:1080.

2Explicit refs have one result contract

StateResult

Remote confirms that the ref is absentFail closed and remove its stale cached identity
Remote is unavailable; exact direct cache identity existsUse it only when non-strict fallback is allowed
Fetched content is not a commitFail closed
Value is a symbolic default such as HEADReject it before fetch

Public skill, plugin, and extension interfaces do not change. The resolver remains shared internal infrastructure. Sources: validation, remote selection, skill caller.

3Risk and review scope

⚠ Compatibility fallback: A restrictive Git protocol-v0 server can reject a direct request for an unadvertised commit ID. If the configured fetch still cannot resolve it, the resolver fetches all remote branch and tag history, then verifies the requested commit ID.
  • Remote absence must not become an offline fallback.
  • A symbolic cached ref must not satisfy an exact identity check.
  • A fetched object must resolve to the requested commit identity.
  • Detached checkout must remove dirty tracked cache content.

Regression sources: dirty cache, symbolic cache ref, deleted branch, shallow detached checkout.
