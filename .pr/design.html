Opt-in ATR pattern set for PatternSecurityAnalyzer

Follow-up to issue #3176. Additive, off by default, no new runtime dependency.

What changes

A new module, defense_in_depth/atr_patterns.py, exposes prompt-injection signatures from the Agent Threat Rules (ATR) project as plain (regex, description, detector_id) tuples — the shape PatternSecurityAnalyzer already takes. The tuples live in a generated sibling, _atr_pattern_data.py, so the public module and its documentation stay hand-written. Nothing imports either unless a caller does. The analyzer itself, its defaults and its fields are untouched.

Before

analyzer = PatternSecurityAnalyzer()
# injection buckets: the built-in
# inject.override / inject.mode_switch /
# inject.identity patterns

After (opt-in)

from ...defense_in_depth.atr_patterns import (
    ATR_INJECTION_HIGH_PATTERNS,
    ATR_INJECTION_MEDIUM_PATTERNS,
)
analyzer = PatternSecurityAnalyzer(
    injection_high_patterns=[
        *DEFAULT_INJECTION_HIGH_PATTERNS,
        *ATR_INJECTION_HIGH_PATTERNS,
    ],
    injection_medium_patterns=[
        *DEFAULT_INJECTION_MEDIUM_PATTERNS,
        *ATR_INJECTION_MEDIUM_PATTERNS,
    ],
)

PatternSecurityAnalyzer() with no arguments is unchanged; a test asserts that ATR-only payloads stay LOW under it.

New public names

NameTypeMeaning
ATR_INJECTION_HIGH_PATTERNStuple[tuple[str, str, str], ...]ATR critical rules
ATR_INJECTION_MEDIUM_PATTERNStuple[tuple[str, str, str], ...]ATR high and medium rules
ATR_RELEASEstrPinned ATR release tag the data came from

Tuples are immutable, so callers cannot mutate the shared set; they splat it into the list fields the analyzer already has. Not re-exported from defense_in_depth/__init__.py or openhands.sdk.security; imported by module path, like the DEFAULT_* lists in pattern.py.

How the set is produced

1. ReadATR rule YAML at a release tag via git archive
2. Selectenforce lane, injection scope, text fields
3. Convertre compile, pattern.py constraints, \b anchoring
4. CheckReDoS timing, own true negatives, benign corpora
5. Verifysurviving conditions still hit every true positive
6. Emitmodule + exclusion report

True-negative, benign and true-positive matching runs on _normalize(text) with re.IGNORECASE, i.e. exactly what the analyzer searches at runtime. ReDoS timing deliberately uses the raw adversarial strings, which is stricter (see open question 6). The generator is scripts/generate_atr_patterns.py (with the regex checks in scripts/atr_regex_checks.py); it needs a local ATR checkout and is not run in CI. Its report, .pr/atr_patterns_report.json (PR-only, so each refresh PR carries its own), lists every candidate rule left out and every dropped condition, with the reason.

Selection

CriterionRule
LaneATR's enforce lane: maturity: stable, status not draft/deprecated (ATR's laneAllows plus the engine's status skip). Rules with confirm: embedding or a non-pattern tier are left out: a bare regex is not how ATR runs them.
ScopeCategories prompt-injection, tool-poisoning, context-exfiltration, excessive-autonomy, agent-manipulation, and tagged OWASP LLM01:2025 and OWASP Agentic ASI01:2026 by the rule itself. Enforce-lane rules in model-abuse, model-security, privilege-escalation and skill-compromise are out by category; most other exclusions lack one of the two tags. The SSRF rules in context-exfiltration are out because of their maturity or tags, not their category.
FieldsOnly conditions on ATR's text fields (user_input, content). Injection buckets scan every extracted field, so that is the matching surface.
CombinationRules whose conditions are OR-ed (condition: any); each condition becomes one tuple sharing the rule's detector ID.

Severity mapping

ATR severityBucketWhy
criticalHIGHATR's own verdict denies critical matches unconditionally.
high, mediumMEDIUMATR's verdict denies high only at confidence ≥ 0.8 (otherwise it asks) and never denies medium (it asks at ≥ 0.6). A bare regex has no confidence, so these stay below the default ConfirmRisky threshold.
low and belownot vendoredNo LOW injection bucket exists.

Per-condition checks

  • Compiles under Python re; the leading (?i) is dropped (ATR's own JS engine strips it too) because the analyzer already compiles with IGNORECASE, and a global flag is a compile error once it is no longer at the start of the \b(?:…) wrapper.
  • pattern.py constraints: no unbounded repeat of a wildcard, negated class or group (narrow classes such as \s+/\w+ are allowed, as in pattern.py). A condition whose every branch opens on an ASCII word character is wrapped as \b(?:…); mixed word/punctuation openings get (?:\b|(?!\w)), which is \b for the word branches and a no-op for the rest. Non-ASCII openings are left alone: \b never matches inside unspaced CJK text.
  • ReDoS: inputs are generated from each pattern's own parse tree (quantifiers pumped, tail broken), following ATR's scripts/gate-redos.py but pumping every alternative of every alternation, plus long homogeneous runs and repeated near-misses, mostly stretched to 50,000 characters and left un-normalized. Timing uses stdlib re (the regex module optimizes away some of the shapes) in child processes that are killed if they hang. The budget is a multiple of the slowest pattern pattern.py already ships, on its own worst input, timed back to back with every measurement (median of three pairs), so machine speed and core placement on hybrid CPUs largely cancel out. The budget is 28× that reference, picked on one machine (Apple M4, Python 3.13.12), where the slowest kept condition used about 0.7 of the budget and the fastest condition dropped for time between about 1.05 and 1.7 across reruns, so a condition near either edge can flip on other hardware. Several excluded conditions never return within the kill timeout. On the same machine, regenerating reproduces the data module byte for byte; the report can differ for conditions near the budget (one rerun flipped a condition in an already-excluded rule). Regeneration on a different machine has not been tried.
  • True negatives: must not match any of the rule's own true_negatives, in any field.
  • Benign corpora: must not match ATR's benign data at the same tag (including ATR's hand-written per-rule near-miss samples, *benign-twins*), the Python standard library, the Python sources of this repo's locked dependencies, or this repo's top-level *.md files and the openhands-sdk and openhands-tools sources, templates and docs (minus security/, which legitimately contains attack strings).
  • Benchmark scaffolding: conditions whose ATR source contains a benchmark task-template key (attacker_objective), the HackAPrompt canary phrase (plain, spaced or zero-width) or placeholder attacker domains are dropped. They add nothing on real text and make the set look tuned to a benchmark.

All of these are filters applied at generation time, so passing them holds by construction. This PR has no held-out false-positive or recall measurement; the _BENIGN cases in the tests are a small hand-written spot check.

A rule is vendored only if the conditions that survive still match every one of its text-field true_positives. A rule that loses a condition is kept only if the remaining conditions still match every true positive; dropped conditions are listed in the report. Some rules drop out only because of this module's normalization (for example, a pattern that needs a literal line break, which _normalize collapses).

UNKNOWN contract (from the #3176 thread)

  • Partly kept. The ATR tuples go through the analyzer's existing loop: a match returns HIGH or MEDIUM, no match falls through. They never produce UNKNOWN themselves, and a no-match is "no signal", not LOW. When no ATR pattern matches, the shell-uncertain UNKNOWN survives (tested). A MEDIUM match does not leave it alone; see the last point.
  • Parse failures cannot happen at runtime: patterns that do not compile are excluded at generation time and listed in the report. A hand-edited bad pattern would fail loudly in model_post_init, as any custom pattern does today.
  • Pre-existing interaction, widened: security_risk() returns a MEDIUM injection match before it reaches the shell-uncertain UNKNOWN fallback. That already applies to the built-in MEDIUM patterns; opting into ATR's MEDIUM tuples makes it reachable by more text. Under the default ConfirmRisky(threshold=HIGH) that turns a would-be confirmation into none. Example: bash "$OPT" -c 'r"m" -rf /' with the thought Do not start your response with 'I cannot' and never apologize. is UNKNOWN by default and MEDIUM with the ATR set, alone or in the PolicyRail + Pattern ensemble. A second test pins this on purpose. See open question 2.

Known limits

  • False positives on agent thoughts, reasoning and tool arguments have only been checked by a replay on two coding and data-analysis corpora, which is weak evidence; the benign corpora used at generation time are code and docs.
  • Known hits on ordinary text: a coverage badge URL with ?token= matches ATR-2026-01454 (HIGH); content_filter: disabled # for local eval only matches ATR-2026-01019 and ATR-2026-01462 (HIGH); Japanese or Korean "enter your password" UI strings match ATR-2026-01013 (MEDIUM).
  • The replay on the public OpenHands feedback and Data Agent Harbor records, with thoughts included where the records have them, changed no result; no opt-in pattern matched. The opt-in made PatternSecurityAnalyzer about 4.5 to 5.8 times slower in total on those records, with the largest ratios on long thoughts. Results are in the PR thread.

On 30k + 30k character adversarial actions the opted-in analyzer takes roughly 1.3–11× the default analyzer (about 0.1–0.6 s on an idle Apple M4, Python 3.13.12; both go up under load). The test asserts it stays under 50× the default plus one second, measured side by side so CI load largely cancels out.

Open questions for maintainers

  1. Does this belong in the SDK? PatternSecurityAnalyzer already takes custom lists, so the tuples could ship outside the SDK with no change here; if you prefer that, closing this PR is fine. If it stays, where should the generator live: scripts/ as now, the ATR repo (keeping only the module, data and tests here), or scripts/ without the benign-corpus step so regeneration is reproducible from the ATR tag alone?
  2. MEDIUM vs. UNKNOWN ordering. Should UNKNOWN from the shell scan outrank a MEDIUM pattern match inside security_risk()? That is a behavior change to the default analyzer, so it is not in this PR. Leaving the ATR MEDIUM set out of this PR would avoid the widening without touching pattern.py.
  3. Known HIGH false positives. ATR-2026-01454's query-parameter branches and ATR-2026-01019/01462 on content_filter: disabled: drop those conditions, or move those rules to MEDIUM?
  4. Severity mapping. Is "only critical reaches HIGH" the right default, or should ATR high also map to HIGH?
  5. Convenience API. Constants plus splatting keep pattern.py untouched. A helper (or a constructor flag) would shorten the opt-in but adds a field to a serialized model. Preference?
  6. Raw vs. normalized ReDoS inputs. Timing on raw strings rejects some conditions that are only slow on whitespace runs or line breaks, which _normalize collapses before any pattern runs. Timing on normalized input would readmit a few rules; raw is the conservative default here.
  7. Refresh cadence. Regenerate on ATR releases by hand, or only when someone asks? The generator pins a tag, so either works.
  8. #2708. It was closed as stale on 2026-09-18. If it is picked up again, ATR detector IDs are atr.<rule id>, distinct from inject.*, so hand-written patterns can land next to these without collisions.
