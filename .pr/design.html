Pause requests remain active until the step stops

An ACP step is a whole remote prompt turn. Tools may keep running after /pause; existing clients must keep waiting until the prompt stops.

1. Contract2. Responsibilities3. Evidence

1. Distinguish the request from completion

Staged migration. Internal state is PAUSING; current REST, WebSocket and webhook contracts continue to report RUNNING until the step stops. No new flag or capability declaration is added. Python and TypeScript clients accept PAUSING for a future server release. The full REST compatibility check now passes.

2. Keep status consumers consistent

ResponsibilityChange and reason
Run loopsConsume pause intent at a step boundary; a true return stops the loop while preserving confirmation, errors and a FINISHED step. A finished step becomes PAUSED only when a message was queued during it, so resume picks the message up instead of re-running a completed turn. Repeated requests do not duplicate PauseEvent. IDLE pauses immediately. run()/arun() accept a stale PAUSING state like any other resumable one.
Loop-less pausespause() checks for an active run loop (the cancellation token). Without one, RUNNING or IDLE lands PAUSED immediately, as before PAUSING existed; otherwise interrupt()'s pause fallback would leave PAUSING forever, reported as running.
Native confirmationReject an action superseded by a new message before pausing. Otherwise preserve WAITING_FOR_CONFIRMATION, so resume is not presented as approval.
ACP finalizationKeep PAUSING until the loop decides the outcome at the boundary: a completed prompt with nothing queued finishes, otherwise it pauses. Query last_prompt_completed through a read-only ACPAgent property so interruption during cleanup cannot replay the prompt. Reset it before each sync or async step.
Remote waitingClients accept PAUSING as active work; current servers send RUNNING while a pause is pending. Concurrent /run remains HTTP 409.
Startup recoveryReuse active-state recovery for stale PAUSING. Catalog startup loads those records; they become ERROR without automatic replay.
Runtime retentionExclude PAUSING from idle eviction. RUNNING and PAUSING share is_active().
Gateway and telemetryThe Chat Completions reused-conversation wait and the telemetry subscriber treat PAUSING as an observed run via is_active(). The ACP supersede check deliberately stays RUNNING-only: once a pause is pending, a new message is queued rather than interrupting and auto re-running, so the stop intent wins.
Wire compatibilityOne projection serves conversation responses, REST event reads, WebSocket and webhook events. It preserves internal objects and persisted state. RUNNING searches/counts include pending pauses; response schemas retain the old enum values.
TypeScript snapshotsRecognize both full_state and the legacy __full_state__ key, so a later PAUSED update is not hidden by an old PAUSING snapshot.
API types and docsAdd the Python/handwritten TypeScript enum value and describe the boundary. Generated TypeScript schema stays tied to its released server image pin.
