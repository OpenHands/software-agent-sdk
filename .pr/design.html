Issue #16905 · SDK / Agent Server design

Structured launch-time skill overlays

Let a deployment attach complete Skill objects after an agent or Agent Profile is resolved, without overloading the system-message suffix or changing the stored profile. This preserves native ACP skill sourcing while making deployment-owned, per-turn skills available to the conversation.

Additive API Reusable capability Order-sensitive application

Why a new field?

Profiles are resolved server-side A client launching by profile id cannot place deployment context directly on the resolved agent.
Native ACP sourcing intentionally strips skills Profile-managed skills are removed so a host ACP runtime can use its own home-directory skills.
A skill is not a text suffix It carries a trigger, metadata, invocation policy, and potentially more than 32 KiB of content.
i

The existing system_message_suffix_append is capped at 32,768 characters and is always-on prompt text. Encoding a skill there would lose trigger semantics and inflate every turn. The new field keeps the object structured.

Public API: before and after

Before

Launch additions could append only a bounded text suffix.

class AgentLaunchAdditions(BaseModel):
    model_config = ConfigDict(extra="forbid")

    system_message_suffix_append: str | None = Field(
        default=None,
        max_length=32768,
    )

After

A full SDK Skill list can be supplied alongside the suffix.

class AgentLaunchAdditions(BaseModel):
    model_config = ConfigDict(extra="forbid")

    system_message_suffix_append: str | None = Field(
        default=None,
        max_length=32768,
    )

    skills_append: list[Skill] = Field(
        default_factory=list,
    )
{
  "agent_profile_id": "…",
  "agent_launch_additions": {
    "skills_append": [{
      "name": "openhands-automation",
      "content": "# OpenHands Automations\n…",
      "trigger": { "type": "keyword", "keywords": ["automation"] },
      "disable_model_invocation": true
    }]
  }
}

Request lifecycle

Merge contract

  • The resolved context is the primary collection; equal-name launch skills do not overwrite it.
  • Names in disabled_skills stay disabled, including overlay entries.
  • Unique overlay skills are appended in request order.

Persistence contract

  • agent_launch_additions remains launch-only and is excluded from stored request data.
  • The resulting AgentContext is persisted with the materialized agent.
  • On restart, per-turn trigger evaluation uses the same skill and full content.

Compatibility and boundaries

Additive for existing clients

  • The field is optional and defaults to an empty list.
  • Requests that omit it preserve current resolution, sourcing, and persistence behavior.
  • No profile data or migration is required; changes are scoped to the launched conversation.

Intentional guardrails

  • The SDK API is agent-agnostic; downstream clients decide when to send an overlay.
  • The overlay happens after native ACP stripping. Reversing this order would delete the new skills.
  • Older servers reject this unknown field, so server and client rollout order matters.

Release sequence

Land server capability

SDK model, Agent Server ordering, persistence, and tests.

Publish schema

Release the Agent Server OpenAPI surface containing skills_append.

Regenerate clients

Publish typed clients from that released schema.

Enable downstream use

Send enabled deployment skills only after compatible servers are deployed.
↩

Rollback: stop sending skills_append. No stored profile or database migration needs to be reversed.
