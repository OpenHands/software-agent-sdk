A pause request is not a completed pause

The current ACP turn may continue running tools after a pause request. This change exposes that interval as PAUSING, keeps clients waiting, and reports PAUSED at the boundary. Resume consumes the next queued prompt.

1. Status becomes a truthful execution contract

★ Draft compatibility decision: older Python clients reject pausing. This direct-status proposal needs a rollout or compatibility mechanism satisfying the repository's five-minor-release policy before upstream submission.

Before
POST /pause → HTTP 200
execution_status: "paused"
ACP tools may still execute
After
POST /pause → HTTP 200
execution_status: "pausing"
step finishes → "paused" + PauseEvent

Enum and shared active-state predicate: openhands-sdk/openhands/sdk/conversation/state.py:48

2. Completion owns PAUSED and PauseEvent

An ACP step is a whole remote prompt turn. pause() does not send session/cancel. interrupt() still requests cancellation. If execution fails while pausing, ERROR/STUCK is preserved. A stale active state after a server crash becomes ERROR using existing recovery; it is not automatically retried.

3. Each consumer agrees on active execution

Pause intent is completed at the step boundary

The run loops share _finish_pending_pause(). It emits PauseEvent at a boundary and preserves ERROR/STUCK. Repeated requests are idempotent. IDLE pauses immediately; an existing confirmation wait is unchanged. The old ACP event-log scan is removed.
