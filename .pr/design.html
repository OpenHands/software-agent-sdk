3. Disk failure has its own stop path

Before

Generic run failure attempts another persisted status and error event. Disk exhaustion can make that error handling fail too.

After

Admission and five-second watchdog checks latch storage pressure. Started results may use remaining capacity to persist completion. Persistence failure suspends writes and sends a direct callback, including failures outside the run loop. Recovery does not replay uncertain tools.

Fig. 2: low-space admission preserves committed state; a write failure needs explicit review before recovery.

check_storage_safety_paths · storage_safety.py:96 admits work only when the free-space floor remains. Before each ordinary write, it also budgets the complete UTF-8 temporary-file size. Exactly 5% free can pass a zero-byte admission check, but a write must still leave the configured reserve. In-flight completion may use that reserve; it is not preallocated space.

After the main model returns, optional CriticMixin._evaluate_with_critic · agent/critic_mixin.py:50 checks admission again. A latched storage stop skips that extra model work and preserves the completed primary response for the run loop to handle.

One write-failure latch for conversation data and server metadata

With storage safety enabled, EventService.start supplies a LocalFileStore to LocalConversation. Its StorageSafetyController guards event files, base_state.json, and subsequent save_meta writes to meta.json. A metadata write failure therefore stops SDK admission through the same latch. Before that shared store exists, the server performs a preflight capacity check and converts metadata write failures to structured storage errors.

EventService.recover_storage holds the run lock, performs SDK recovery off the event-loop thread, retries metadata persistence, then clears its storage error and publishes a state snapshot.

Recovery caseResult and required review
Low-space admission stop; committed state is intactRecheck capacity and clear the stop latch. Preserve the selected HEAD and execution status; an idle conversation stays idle.
Write failure in the same processRequire acknowledge_unknown_outcomes=true. Retain the known HEAD, record missing tool outcomes as unknown, persist the repaired state and leave execution paused.
Ambiguous history after a cold restartRequire acknowledgment and explicit head_event_id chosen after inspection. Never walk existing children to guess which branch should be active.
Explicit continuationCall run/arun separately. Recovery never schedules a run.

This is early-stop protection, not a filesystem quota. Other processes and already-running tools can exhaust the reserve. Committed records remain; uncommitted outputs cannot be promised recoverable after process exit. No automatic history deletion, TTL, compression format, or external archive is introduced.
