Durable event sequence allocation

Repair duplicate and reused replay cursors after supported event-file loss. Public Python methods, event JSON, REST payloads, and session WebSocket frame shapes stay unchanged.

Observed failure

Writer A stores events at sequences 0, 1, 2. After file 1 disappears, writer B reopens and appends at sequence 3. Both logs now have dense length 3. The old length marker lets A skip refresh: A rejects B's event as a parent and allocates sequence 3 again. A reconnect after sequence 3 skips A's new event. Losing the last file also lets a restart reuse its sequence. Native local storage and the real server restart/reconnect path reproduce this.

Before: a:0, c:2, d:3, e:3     after_seq=3 → []
After:  a:0, c:2, d:3, e:4     after_seq=3 → [e]

Allocation protocol

existing FileStore lock
  refresh if the expected next reservation exists or the count marker differs
  validate event ID and parent
  existing write guard / conversation lease
    publish immutable .eventlog-seq-N.marker
    publish event-N-ID.json
  publish in-memory dense index and existing count marker
release lock

A reservation survives failed publication and lost event files. Cold scans allocate after both the highest surviving filename and every retained reservation. A stale writer probes its expected next reservation with one exists(); old reservations remain, so it cannot miss a later writer that has already advanced several times.

Reservation contents are immutable and empty. No mutable metadata read depends on FileStore cache freshness, and no FileStore interface or backend dependency is added.

Compatibility and failure behavior

SurfaceBehavior
append(event)Returns the existing dense index, including after holes.
get_seq / after_seqContinue using durable physical sequence numbers; failed writes may leave gaps.
Old event filesRead in place. Existing length markers provide a legacy high-water hint.
Unreadable directoryRead construction keeps its existing tolerance; append requires a successful refresh and does not guess an empty writable log.
Missing directoryStill permits a new store's first append.
Navigation and forkBranch selection does not lower a conversation's allocation watermark. Forks allocate in their own directory.

Costs and limits

One empty reservation file is retained per allocated sequence. It is part of the log, not disposable cache; deleting it can invalidate stale-writer detection and recovery. The steady-state append path still avoids directory scans. Scans remain proportional to stored event and reservation filenames.

This does not recover deleted event payloads, retroactively renumber already-corrupt duplicate sequences, or infer an old lost sequence when no legacy metadata records it. Mixed writers running older SDK code do not participate in the new allocation protocol. NFS coordination retains the FileStore's existing documented limitations.

Verification

Tests exercise native local/in-memory stores, warm concurrent writers, process death before and after event publication, denied scans, lease guard rejection, legacy markers, real conversation resume/navigation/fork, and real REST → restart → WebSocket cursor replay. REST messages use run=false; no agent step or paid model call is needed.
